# Сопровождение поиска

Заметки для разработчиков, которые меняют поиск: формат хранилища, как приложение перезапускает
воркер, что воркер может писать в журнал, и проверки вне обычного прогона тестов. Как поиск
выглядит для пользователя, описано в разделе [Поиск](search.ru.md); образцы CBOR протокола воркера —
в [search/testdata/protocol/README.md](../search/testdata/protocol/README.md), подготовка модели — в
[tools/model/README.md](../tools/model/README.md).

- Формат хранилища 2 необратим. `internal/adapter/sqlite` переводит хранилище формата 1 в формат 2
  (таблица `note_embedding`) при первой разблокировке, после проверки пароля, одной транзакцией;
  2.0.0 и 2.0.1 после этого отказываются его открывать с сообщением «Data was created by a newer
  version of Smartnote.». Единственный путь назад — Backup на сервер в новой версии и Restore в
  новое хранилище 2.0.x ([Установка и обновление](install.ru.md#обновление-с-20x)).
- Перезапуски воркера (`internal/adapter/searchworker/backoff.go`): паузы 1, 2, 4, 8, 16 с; движок
  сдаётся после 5 неудачных перезапусков за 10 минут (на шестом сбое), и поиск остаётся недоступным
  до следующего запуска. Пока ни один воркер не готов, а также когда поиск не уложился во время,
  `Search` возвращает `usecase.ErrSearchUnavailable` (в интерфейсе — `Search unavailable`, никогда
  не `No matches`); три превышения времени поиска подряд перезапускают воркер. Поисковая строка
  повторяет текущий запрос, когда поиск по словам становится готов; `usecase.Search` придерживает
  статусы, пока в очереди стоит пересборка (до её маркерной команды `rebuilt`), чтобы этот запрос
  никогда не попал в пустой индекс нового воркера.
- То, что пишет воркер, попадает в `smartnote.log` только в виде закрытого словаря и в пределах
  бюджета на один запуск приложения (`internal/adapter/searchworker/stderr.go`, `workerOutput` у
  `Engine`; перезапуски его не обновляют): строка stderr записывается, если она совпадает с одной
  из форм там, без свободного текста (сообщения ОС об ошибках, места в ONNX Runtime и файлы вне
  воркера опускаются; паника называет свой файл, только если он есть в `workerSourceFiles`), иначе
  как `search worker stderr: unrecognized line` с её длиной; `msg` ответа с ошибкой — только если
  он есть в `knownErrorTexts` (`protocol.go`). Не больше 64 записей stderr, 64 текстов ошибок,
  8 строк паники и 8 строк ONNX Runtime за запуск; затем одна строка «search worker: further worker
  output dropped», а `Close` записывает счётчики. То, что выбирает воркер (числа, выбор из
  фиксированных текстов, длины), — не больше примерно 0,6 КБ за запуск (около 72 бит на запись ×
  64, 3 бита на текст × 64, два счётчика). Не покрыто: код ответа с ошибкой, а также статус выхода и
  время упавшего процесса (их ограничивает правило перезапусков за 10 минут, а не запуск). Новый
  `eprintln!` или новый исходный файл в `search/worker/src` требует своей формы или записи в
  `workerSourceFiles`: `TestStderrFormsCoverWorker` читает исходники воркера и падает, пока её не
  добавят.
- `make search-asan` запускает небезопасный код (обнуляющий аллокатор `search/zalloc`, усиление и
  песочницу воркера, `-p worker --lib`) под AddressSanitizer (`RUSTFLAGS=-Zsanitizer=address`,
  `--target x86_64-unknown-linux-gnu`). Ему нужен ночной набор инструментов
  (`rustup toolchain install nightly`), и в CI он не входит. Последний запуск — 2026-11-05 с nightly
  1.101.0 (708c94ef0 2026-11-03): `zalloc` 3 + 4 теста, `worker` 126 тестов, сообщений санитайзера
  нет.
- В CI (`CI=true`) на Linux с feature `test-probes` `search/worker/build.rs` завершается ошибкой,
  если нет `gdb` или `strace`, вместо того чтобы пометить их тесты пропущенными: тест дампа памяти
  и тест системных вызовов — доказательства для спецификации поиска (критерий 5). Локально
  отсутствие инструмента по-прежнему только пропускает его тест.
